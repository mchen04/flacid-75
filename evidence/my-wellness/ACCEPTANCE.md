**Account receipt (current)**: every answer from the account (a read or a write) carries a receipt: the ids of the most recently applied changes (bounded to 200) and the revision (the account's count of applied changes), taken from the same database snapshot as the state (one statement; under the row lock inside a write). Before an answer's state is used, every change this device still holds that the receipt lists is acknowledged, so a change another tab made during this tab's request is never applied a second time on top of a state that already contains it. An answer whose revision is below the one the device holds is not installed. When the receipt is full (200 ids) and more than 200 changes were applied since the revision this device last saved, a held change that is not listed, not in this write's own answer, and marked sent (a write holding it is in flight or was answered) is not projected onto the state; it stays pending and is presented in the write that follows at once, which the account answers exactly (a recorded id is accepted again, applied once). A change whose write failed without an answer, or that was never sent, is always projected. Unlock applies the same rule. Answers without a receipt fall back to the save counter.

**Generation fence (current)**: a durable local counter (`my-wellness-generation`) advances on every lock-and-clear. Every tab remembers the generation it loaded and every request remembers the generation at which it started. A snapshot write, a storage merge, a dispatch, a sync answer or an unlock answer from an earlier generation is refused; the tab drops its memory and adopts the current saved store instead. The lock marker still fences writes while the device is locked; the generation fences stale memory after a legitimate new unlock. Nothing is cleared on the account.

**Cross-tab note (current)**: the device store has four durable parts and every snapshot write merges all of them with what is saved (`persist`): the queue, the per-change journal keys, the refused list with its discard record, and the acknowledged record (`acked`, the ids the account has accepted or refused, bounded to the last 500) with a save counter (`epoch`). A tab's memory is never a source of pending changes: what is pending is the saved queue plus the journal minus the acknowledged record, so a change one tab still holds after another tab's acknowledgement is neither re-queued nor re-applied. An account answer whose request began before another answer was saved (`epoch` moved) is not installed: a read is repeated at once, a write's acknowledgements are recorded and a read follows. Acknowledgements are saved before the journal keys are removed, so a refusal answered while storage refuses the snapshot stays journaled and is answered again. Lock and clear writes a marker key first; every tab that sees the marker or the snapshot's removal locks itself, and no snapshot or journal write is accepted while the marker stands, so a stale tab or a late answer cannot restore cleared data; unlock removes the marker before saving.

**Cross-tab note (historical, b10f0c7)**: writers are not serialized. `dispatch`, `mergeFromStorage` and the sync save all write the snapshot key, and the Web Lock covers only the sync's read-merge-save. What keeps a change safe is that every dispatched change is first written to its own key (`my-wellness-op:<id>`), removed only when the account has accepted it or storage is locked, and unioned back into the queue at every start, sync and storage event. A snapshot overwritten by a stale save therefore cannot lose an acknowledged change; the journal key outlives it. Refused changes have no journal key (the account has answered), so they are protected differently: `persist` merges the refused list by id with the saved snapshot on every write, and an explicit discard is recorded by id so it holds across tabs. Proof: `wellness.spec.ts` "R163-4…" writes another tab's change exactly between this tab's read and its save (a hook on `localStorage.setItem` fires on the post-sync snapshot with an empty queue), then shows the change reaching the account with no other tab open and surviving a reload with one account write.

### Limitations, stated plainly
- **Not verified on a physical device.** Wall-clock timers are verified with a virtual clock in Chromium (reload, 20-minute sleep, midnight). iOS may terminate a backgrounded PWA; on reopen the timer resumes from storage, but no notification or sound fires while the app is closed, and the wake lock only holds while the page is visible. Sound needs a user gesture first, which Start provides. Sound while the phone is locked is not observable here.
- **WebKit, the real server, the disposable database and the real service worker were run by the supervisor and by independent review 175, not in this sandbox.** WebKit does not launch here. The specs are engine-agnostic; every regression added for reviews 163 and 164 is written for both engines and the supervisor's review 164 run executed the earlier ones on both. The runs for this commit are the supervisor's in `final174/` and review 175's in `final175/`.
- **Deployed.** Version 4 was merged into `main` by Michael through [pull request #1](https://github.com/mchen04/flacid-75/pull/1) on 2026-09-11 (merge commit f96cc4b, tree identical to the reviewed 5198e39); GitHub deployment 6386909969 to Production succeeded on the same day, and the live link at the top serves it. Physical iPhone verification of the deployed app remains unfinished.
- **Bundle headroom:** see the current summary above for the exact figures at this commit; the limit is unchanged at 40,960 gzip bytes on the critical path and 65,536 in total.
- **The blind visual comparison** against the references was not repeated by the owner; the reviewer's independent coverage of all 273 frames is recorded in the verdict as seen, not approved.
- **Fixtures are synthetic.** No real personal data or credentials appear in tests or evidence.
- **Bounded records.** The acknowledged record keeps the last 500 ids, the discard record the last 200, and the account's receipt the last 200 applied ids. A held change that has left the receipt is never assumed unacknowledged: it is left unprojected and presented in a write, which is answered exactly.
- **Text limits are characters, not bytes or UTF-16 units.** A 60-character plan line of emoji is about 240 bytes; batches are still bounded by bytes.
- **A sent mark is transport-truthful only as far as the answer goes.** A write that received no 2xx answer is treated as not presented; if the account had in fact applied it, the receipt or the next write's answer (a recorded id is accepted again) settles it once.
- **Judge 175's surviving findings, tracked, none requiring a redesign.** (1) Coverage gap: the automated suite has no test that the water endpoint refuses a locked, cross-origin or malformed request; the reviewer executed those guard checks live (401, 403, 400, `final175/review175-auth.txt`) and the guard is in `app/api/water/route.ts`; an automated mutation test remains a follow-up, not claimed fixed. (2) Pour phrases written with a digit before a word share ("3 quarters of a glass", "2 thirds") and "my third glass" read as a whole or a third; "1 1/2 glasses" reads as half; the confirm card shows the amount before it is added. (3) The oz limits named in the water-target message (16.9 and 202.9 oz) are themselves refused when typed, since they round outside 500–6000 ml; the container form's "1 to 200 oz" wording does not match its 30–6000 ml range. (4) Switching units inside Your details refills the fields from the stored values and drops a typed edit. (5) A refused water undo shows no message on the Water page. (6) The setup sheet saves profile and units as two changes and could half-save under a storage failure (not reproduced). (7) The water route validates by hand, with no body-length cap and 503 for a null body, behind the gate and a 60-per-hour limit. (8) The sent-mark comment overstates certainty for an answer lost after the account committed. (9) Every state read counts the operations table, negligible at one user's volume.
- **Session end on lock is best effort.** The device is cleared first; the request that ends the account session is retried until it answers, and a session that could not be ended is not claimed ended. The database integration checks for receipt coherence are in `scripts/integration.ts` for the supervisor's disposable database; they do not run in this sandbox.
